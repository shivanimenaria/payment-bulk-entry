# rDash API notes — unverified assumptions

Every assumption PBE makes about rDash that has **not** been confirmed by the rDash team or a live call. Each one is marked `TODO(verify)` at the code point that depends on it. When an item is confirmed, record the evidence here and remove the marker.

Status key: **Unverified**: assumed from the Swagger docs, the RFQ app, or the integration brief. **Verified**: confirmed (note how and when).

| # | Topic | Assumption | Code point (`TODO(verify)`) | If wrong | Status |
|---|---|---|---|---|---|
| 1 | ID encoding | rDash ids are Hashids (min length 16) with the PBE per-app salt `EMBEDDED_APPS_HASH_ID_SALT_PBE`. This applies to the iframe URL `vendor_id` / `org_id` / `user_id` / `project_id`, handover `user.id` / `org.id`, `/v2/vendors` `id`, and config/details/bulk `payment_request_id`. The config endpoint's `vendor_id` query parameter takes the hashid of the session vendor. Payment-flow ids (project ids, `payment_request_id`) are passed back to rDash exactly as returned, never decoded. | `src/lib/server/rdash-id.ts` (header); `src/app/api/session/route.ts` (`toIntString`); `src/lib/server/api.ts` (`decodeIdField`); `src/lib/server/rdash-source/real.ts` (`listPaymentRequestConfig`) | URL vendor/org ids fail to decode, giving `vendor_not_found` or `org_mismatch`. A list id that doesn't decode throws `RdashIdDecodeError` (shown as `session_error` at handover). | Unverified |
| 2 | List envelope | List endpoints return `{ data: [...] }` or `{ data: { data: [...] } }`. Paging is `limit` / `offset`, and a page shorter than `limit` means it's the last page. The config endpoint returns `{ data: { count, data: [...] } }`, where `count` is the total number of matching items, and is paged until `count` is reached. | `src/lib/server/api.ts` (`paginateRdash`, `untilCount`) | Any other shape, a missing `count`, or an empty page before `count` is reached throws `RdashResponseShapeError`; it is never treated as an empty or partial list. | Unverified |
| 3 | `/v2/vendors` | Scoped to the token's org; returns `id, name, code` with hashid `id`s; no filter by id (only `name`, `code`, `limit`, `offset`); permission `CAN_ACCESS_MANAGE_VENDOR` (taken from the RFQ docs). | `src/lib/server/api.ts` (`assertVendorInOrg`) | If not org-scoped, the "vendor belongs to org" check proves nothing. If users lack the permission, every handover gives `vendor_forbidden`. With no id filter, every handover pages through all of the org's vendors. | Unverified |
| 4 | Iframe URL | rDash opens `/embedded/bootstrap?vendor_id=…&org_id=…&user_id=…` (`project_id` optional) and never navigates the iframe to `/api/session` directly. | `src/app/api/session/route.ts` (`toIntString`, same marker as #1) | Login-CSRF mitigation options change (see CLAUDE.md Open Items). | Unverified |
| 5 | Handover `app_slug` | The consume response's `app_slug` equals the tab slug configured as `RDASH_PBE_TAB_CODE`. | `src/app/api/session/route.ts` (`app_slug` check) | Every real-mode handover fails with `session_error`. | Unverified |
| 6 | Token lifetimes | The consume and refresh responses always include positive `expires_in` and `refresh_token_expires_in` (seconds), and refresh always returns a new `refresh_token`. | `src/lib/server/auth.ts` (`consumeHandoverCode`, `callRdashRefresh`) | Handover fails (`session_error`), or refresh throws `AuthError` and the iframe re-handovers. Lifetimes are never defaulted and an old refresh token is never reused. | Unverified |
| 7 | Handover `user.email` | Optional; may be absent. | `src/lib/server/auth.ts` (`consumeHandoverCode`) | None: stored as `null`. | Unverified |
| 8 | Value types | Amounts (`request_amount`, `paid_amount`, `payment_due`, tax and total fields, bulk `amount`) are JSON numbers, not decimal strings. `requested_at` / `created_at` are ISO-8601 strings; `due_date` / `payment_date` are `YYYY-MM-DD`. | `src/types/rdash.ts` (header, `BulkPaymentEntryInput.payment_date`) | Totals and validation would compare strings; the bulk request could be rejected. | Unverified |
| 9 | `currency` | The config `currency` is an object whose shape isn't in Swagger; it's typed `Record<string, unknown>`. Whether one vendor can have requests in mixed currencies is unknown. | `src/types/rdash.ts` (`VendorPaymentRequestConfigItem.currency`) | Currency display and totals can't be built until the shape is known. | Unverified |
| 10 | Config `project_id` | Requested from rDash; **not in Swagger yet**. It's typed as optional. Rows without it skip the details call and are marked `detailsUnavailable` (no guessing, no default project). Present in mock data only. It's assumed to be the same id that the details path and `/v2/projects` `id` use. | `src/types/rdash.ts` (`VendorPaymentRequestConfigItem.project_id`); `src/lib/server/rdash-source/allocation-rows.ts`; `src/lib/server/rdash-source/mock.ts`; `mock-data/README.md` | Until rDash adds it, real rows show "Details pending" and can't be paid. | Unverified |
| 11 | Details `requested_by` / `attachments` | Swagger names these fields but not their shape. `requested_by` is assumed to be a display string (it could be a user object); `attachments` is typed `unknown[]`. | `src/types/rdash.ts` (`PaymentRequestDetails`) | The Requested By column would render wrongly. | Unverified |
| 12 | Bulk output | `count` is the number of created entries; `failed[].error` is a message string; a partial failure comes back as 2xx with `failed[]` (not a 4xx). | `src/types/rdash.ts` (`BulkPaymentEntryCreateOutput`, `BulkPaymentEntryFailed`); `src/lib/server/rdash-source/real.ts` (`createBulkPaymentEntries`) | A partial failure would throw `RdashUpstreamError` and lose the created/failed split. | Unverified |
| 13 | Bulk body | `{ entries: [...] }`, not `{ data: { entries } }`, switchable via the single constant `BULK_BODY_WRAPPER`. The maximum number of entries per call is unknown. | `src/lib/server/rdash-source/real.ts` (`BULK_BODY_WRAPPER`) | rDash rejects the request (flip the constant). Too many entries could need chunking. | Unverified |
| 14 | Details request | `GET /v2/projects/{project_id}/vendor-payment-requests/{payment_request_id}` (no trailing slash) takes the config's ids unchanged and returns the standard `{ success, data }` envelope. Whether config `payment_request_id` equals details `id` is a CLAUDE.md Open Item. | `src/lib/server/rdash-source/real.ts` (`getPaymentRequestDetails`) | Every details call fails and every row shows `detailsError`. | Unverified |
| 15 | **TEMPORARY** `RDASH_TEMP_PROJECT_ID` | Until rDash returns `project_id` in the config response, a config row without it uses this project for the details call. The row gets `projectIdSource: "temporary"` and the UI marks its project name "(temporary)". The config item is not modified. Bulk submit is unaffected (it uses only `payment_request_id`). Refused under `NODE_ENV=production` unless `ALLOW_TEMP_PROJECT_ID=true`; a warning is logged on every startup while it's set. **Remove `RDASH_TEMP_PROJECT_ID` once config returns `project_id`.** Every use is marked `TODO(remove-temp-project-id)`. | `src/lib/runtime-config.ts` (`resolveTempProjectId`); `src/instrumentation.ts`; `src/lib/server/rdash-source/allocation-rows.ts`; `src/types/payments.ts` (`projectIdSource`); `.env.example` | A request from another project fails its details call, giving `detailsError` with the row kept. If rDash's details endpoint doesn't check the request belongs to the project in the path, it could return details while the shown project name is wrong; that is why the name is marked "(temporary)". | Temporary workaround |
